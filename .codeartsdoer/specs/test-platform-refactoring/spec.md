# 测试平台功能重构需求规格说明书

## 文档信息
- **功能名称**：测试平台功能重构
- **文档版本**：v1.0
- **创建日期**：2025-01-06
- **文档状态**：待评审

## 1. 引言

### 1.1 背景
当前测试平台在设计之初考虑不够全面，导致在不同的测试类型（接口测试、UI自动化、性能测试等）下都存在独立的项目管理、测试报告、定时任务、通知列表等功能模块。这种设计造成了功能割裂、代码重复、维护困难和用户体验差等问题。

### 1.2 目标
将分散的功能模块统一成一个整体，支持根据不同的测试类型进行区分，实现：
- 功能统一管理
- 按测试类型数据隔离
- 代码复用和可维护性提升
- 统一的用户界面和交互体验

### 1.3 范围
本需求规格说明涵盖以下核心功能模块的重构：
- 项目管理模块
- 定时任务模块
- 通知配置模块
- 测试报告模块

**不包含范围**：
- 各测试类型的核心业务逻辑（如API测试执行、UI自动化执行、性能测试执行）
- AI 相关功能
- 数据工厂、知识图谱等其他独立模块

## 2. 功能需求

### 2.1 统一项目管理

#### 2.1.1 项目模型统一
**需求描述**：系统应提供统一的项目模型，支持不同测试类型的项目管理，通过项目类型字段进行区分和处理。

**验收标准**：
- **WHEN** 系统初始化时，**THEN** 系统应创建统一的项目数据表，包含项目类型字段
- **WHEN** 用户创建新项目时，**THEN** 系统应支持选择项目类型（接口测试、UI自动化、性能测试、通用项目）
- **WHEN** 用户查询项目列表时，**THEN** 系统应支持按项目类型筛选
- **WHEN** 用户查看项目详情时，**THEN** 系统应显示项目类型以及该类型特有的属性

#### 2.1.2 项目成员管理统一
**需求描述**：系统应提供统一的项目成员管理功能，支持不同角色权限的分配，所有测试类型共享同一套成员管理机制。

**验收标准**：
- **WHEN** 项目所有者添加成员时，**THEN** 系统应支持分配角色（负责人、管理员、开发者、测试者、观察者）
- **WHEN** 项目成员访问项目时，**THEN** 系统应根据角色分配相应的操作权限
- **WHEN** 成员离开项目时，**THEN** 系统应移除该成员对该项目及其关联资源的访问权限
- **WHEN** 项目被删除时，**THEN** 系统应级联删除或归档该项目下的所有关联资源

#### 2.1.3 项目环境管理统一
**需求描述**：系统应提供统一的项目环境管理功能，支持多环境配置（开发、测试、预发布、生产），环境变量和配置在不同测试类型间共享。

**验收标准**：
- **WHEN** 用户创建项目环境时，**THEN** 系统应支持配置环境名称、基础URL、环境变量
- **WHEN** 用户切换环境时，**THEN** 系统应加载该环境的变量配置
- **WHEN** 用户执行测试时，**THEN** 系统应根据项目类型自动选择默认环境或用户指定环境
- **WHEN** 环境被删除时，**THEN** 系统应提示该环境被引用的测试资源并阻止删除或提供迁移方案

### 2.2 统一定时任务管理

#### 2.2.1 定时任务模型统一
**需求描述**：系统应提供统一的定时任务模型，支持不同测试类型的任务调度，通过任务类型字段区分任务类别。

**验收标准**：
- **WHEN** 系统初始化时，**THEN** 系统应创建统一的定时任务数据表，包含任务类型字段
- **WHEN** 用户创建定时任务时，**THEN** 系统应支持选择任务类型（接口测试、UI自动化、性能测试）
- **WHEN** 用户配置定时任务时，**THEN** 系统应根据任务类型动态显示可关联的测试资源（测试套件、测试用例等）
- **WHEN** 定时任务执行时，**THEN** 系统应根据任务类型调用相应的执行引擎

#### 2.2.2 调度策略统一
**需求描述**：系统应提供统一的调度策略配置，支持 Cron 表达式、固定间隔、单次执行等多种触发方式。

**验收标准**：
- **WHEN** 用户配置 Cron 表达式时，**THEN** 系统应验证表达式格式并计算下次执行时间
- **WHEN** 用户配置固定间隔时，**THEN** 系统应支持以秒、分钟、小时为单位设置执行间隔
- **WHEN** 用户配置单次执行时，**THEN** 系统应支持指定具体的执行日期和时间
- **WHEN** 定时任务触发时，**THEN** 系统应自动更新任务的执行统计信息（总运行次数、成功次数、失败次数）

#### 2.2.3 任务执行日志统一
**需求描述**：系统应提供统一的任务执行日志记录功能，记录每次任务执行的详细信息，包括执行状态、开始时间、结束时间、执行结果等。

**验收标准**：
- **WHEN** 定时任务开始执行时，**THEN** 系统应创建执行日志记录，状态为"执行中"
- **WHEN** 定时任务执行完成时，**THEN** 系统应更新执行日志状态为"成功"或"失败"，并记录结束时间和执行时长
- **WHEN** 任务执行失败时，**THEN** 系统应记录详细的错误信息和堆栈跟踪
- **WHEN** 用户查询执行历史时，**THEN** 系统应支持按任务、状态、时间范围筛选执行日志

### 2.3 统一通知配置管理

#### 2.3.1 通知配置模型统一
**需求描述**：系统应提供统一的通知配置模型，支持多种通知渠道（飞书、企业微信、钉钉、邮件），不同测试类型共享同一套通知配置。

**验收标准**：
- **WHEN** 系统初始化时，**THEN** 系统应创建统一的通知配置数据表
- **WHEN** 用户创建通知配置时，**THEN** 系统应支持选择通知类型（飞书机器人、企业微信机器人、钉钉机器人、邮件）
- **WHEN** 用户配置 Webhook 机器人时，**THEN** 系统应支持配置 Webhook URL 和必要的密钥信息
- **WHEN** 用户配置邮件通知时，**THEN** 系统应支持配置 SMTP 服务器、端口、认证信息和默认收件人列表

#### 2.3.2 通知规则统一
**需求描述**：系统应提供统一的通知规则配置，支持在任务成功、失败、超时等不同场景下触发通知。

**验收标准**：
- **WHEN** 用户配置通知规则时，**THEN** 系统应支持启用/禁用成功通知、失败通知、超时通知
- **WHEN** 定时任务执行成功且启用成功通知时，**THEN** 系统应发送成功通知到配置的通知渠道
- **WHEN** 定时任务执行失败且启用失败通知时，**THEN** 系统应发送失败通知到配置的通知渠道，包含错误信息
- **WHEN** 定时任务执行超时且启用超时通知时，**THEN** 系统应发送超时通知到配置的通知渠道

#### 2.3.3 通知发送记录统一
**需求描述**：系统应提供统一的通知发送记录功能，记录每次通知的发送状态、接收人、发送时间等信息。

**验收标准**：
- **WHEN** 通知发送时，**THEN** 系统应创建通知发送记录，状态为"发送中"
- **WHEN** 通知发送成功时，**THEN** 系统应更新记录状态为"发送成功"，并记录响应信息
- **WHEN** 通知发送失败时，**THEN** 系统应更新记录状态为"发送失败"，并记录错误信息
- **WHEN** 用户查询通知历史时，**THEN** 系统应支持按任务、通知类型、发送状态筛选记录

### 2.4 统一测试报告管理

#### 2.4.1 测试报告模型统一
**需求描述**：系统应提供统一的测试报告模型，支持不同测试类型的报告生成和展示，通过报告类型和项目类型进行区分。

**验收标准**：
- **WHEN** 测试执行完成时，**THEN** 系统应自动生成测试报告，关联到对应项目和执行记录
- **WHEN** 用户查看测试报告时，**THEN** 系统应根据测试类型显示相应的报告内容和统计指标
- **WHEN** 生成接口测试报告时，**THEN** 系统应包含请求列表、响应结果、断言结果、性能指标
- **WHEN** 生成UI自动化报告时，**THEN** 系统应包含测试步骤、截图、错误日志、元素定位信息
- **WHEN** 生成性能测试报告时，**THEN** 系统应包含并发用户数、响应时间、吞吐量、错误率等性能指标

#### 2.4.2 报告模板管理
**需求描述**：系统应提供报告模板管理功能，支持自定义报告样式和内容布局，不同测试类型可以使用不同的报告模板。

**验收标准**：
- **WHEN** 系统初始化时，**THEN** 系统应提供默认的报告模板（接口测试、UI自动化、性能测试各一套）
- **WHEN** 用户创建报告模板时，**THEN** 系统应支持配置模板名称、描述、样式配置、内容布局
- **WHEN** 用户生成报告时，**THEN** 系统应支持选择报告模板，如未选择则使用默认模板
- **WHEN** 报告模板被删除时，**THEN** 系统应检查是否有报告使用该模板，如有则阻止删除或提供替代方案

#### 2.4.3 报告查询和导出
**需求描述**：系统应提供统一的报告查询和导出功能，支持多维度筛选和多种格式导出。

**验收标准**：
- **WHEN** 用户查询报告列表时，**THEN** 系统应支持按项目、测试类型、报告类型、时间范围筛选
- **WHEN** 用户查看报告详情时，**THEN** 系统应支持在线查看报告内容，包括图表、统计数据、详细日志
- **WHEN** 用户导出报告时，**THEN** 系统应支持导出为 PDF、HTML、Excel 等格式
- **WHEN** 用户分享报告时，**THEN** 系统应支持生成报告分享链接，支持设置访问权限和有效期

## 3. 非功能需求

### 3.1 性能需求
- **WHEN** 系统查询项目列表时，**THEN** 查询响应时间应在 2 秒内完成（数据量不超过 10000 条）
- **WHEN** 定时任务触发时，**THEN** 任务调度延迟应在 5 秒以内
- **WHEN** 生成测试报告时，**THEN** 报告生成时间应在 10 秒内完成（测试用例数不超过 1000 个）
- **WHEN** 系统并发访问时，**THEN** 系统应支持至少 100 个并发用户

### 3.2 可扩展性需求
- **WHEN** 新增测试类型时，**THEN** 系统应支持通过配置新增项目类型和任务类型，无需修改核心代码
- **WHEN** 新增通知渠道时，**THEN** 系统应支持扩展通知类型，实现统一的通知接口
- **WHEN** 新增报告导出格式时，**THEN** 系统应支持扩展报告导出器，实现统一的导出接口

### 3.3 数据一致性需求
- **WHEN** 项目被删除时，**THEN** 系统应级联处理该项目的定时任务、测试报告、通知配置等关联数据
- **WHEN** 定时任务被删除时，**THEN** 系统应删除或归档该任务的所有执行日志和通知记录
- **WHEN** 数据迁移时，**THEN** 系统应保证原有数据的完整性和一致性，支持数据回滚

### 3.4 兼容性需求
- **WHEN** 系统重构完成后，**THEN** 应保持对现有 API 接口的兼容，通过适配层支持旧接口
- **WHEN** 前端页面重构时，**THEN** 应保持用户体验的一致性，提供平滑的过渡方案
- **WHEN** 数据库结构变更时，**THEN** 应提供数据迁移脚本，支持从旧版本平滑升级

## 4. 数据迁移需求

### 4.1 项目数据迁移
**需求描述**：系统应提供数据迁移功能，将现有的 ApiProject、UiProject、PerformanceProject 数据迁移到统一的项目模型。

**验收标准**：
- **WHEN** 执行数据迁移时，**THEN** 系统应将所有 ApiProject 迁移到统一项目表，项目类型设置为"接口测试"
- **WHEN** 执行数据迁移时，**THEN** 系统应将所有 UiProject 迁移到统一项目表，项目类型设置为"UI自动化"
- **WHEN** 执行数据迁移时，**THEN** 系统应将所有 PerformanceProject 迁移到统一项目表，项目类型设置为"性能测试"
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的项目成员关系、环境配置等关联数据
- **WHEN** 迁移失败时，**THEN** 系统应提供详细的错误日志，支持回滚到迁移前状态

### 4.2 定时任务数据迁移
**需求描述**：系统应提供数据迁移功能，将 api_testing 应用中的 ScheduledTask 数据迁移到统一的定时任务模型。

**验收标准**：
- **WHEN** 执行数据迁移时，**THEN** 系统应将所有 API 测试相关的定时任务迁移到统一定时任务表，任务类型设置为"接口测试"
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的调度配置（Cron 表达式、间隔时间等）
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的关联关系（测试套件、环境等）
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的执行日志和统计信息
- **WHEN** 迁移失败时，**THEN** 系统应提供详细的错误日志，支持回滚到迁移前状态

### 4.3 通知配置数据迁移
**需求描述**：系统应提供数据迁移功能，将 api_testing 应用中的 NotificationConfig 数据迁移到统一的通知配置模型。

**验收标准**：
- **WHEN** 执行数据迁移时，**THEN** 系统应将所有通知配置迁移到统一通知配置表
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的 Webhook 配置和邮件配置
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的关联关系（项目、定时任务等）
- **WHEN** 执行数据迁移时，**THEN** 系统应保留原有的通知日志记录
- **WHEN** 迁移失败时，**THEN** 系统应提供详细的错误日志，支持回滚到迁移前状态

- **WHEN** 用户进入测试报告页面时，**THEN** 界面应显示所有报告列表，支持按项目、测试类型、报告类型、时间范围筛选
- **WHEN** 用户查看报告详情时，**THEN** 界面应根据测试类型显示相应的报告内容和图表
- **WHEN** 用户导出报告时，**THEN** 界面应支持选择导出格式（PDF、HTML、Excel）
- **WHEN** 用户分享报告时，**THEN** 界面应支持生成分享链接，支持设置访问权限和有效期

## 6. 约束条件

### 6.1 技术约束
- 后端框架：Django + Django REST Framework
- 前端框架：Vue 3 + Element Plus
- 数据库：PostgreSQL（兼容现有系统）
- 任务队列：Celery（兼容现有系统）

### 6.2 业务约束
- 数据迁移必须在低峰期执行，避免影响正常使用
- 必须保证数据的完整性和一致性，支持回滚
- 必须保持对现有 API 接口的兼容，通过适配层支持旧接口
- 必须保持用户体验的一致性，提供平滑的过渡方案

### 6.3 时间约束
- 需求分析和设计阶段：2 周
- 开发阶段：4 周
- 测试阶段：2 周
- 数据迁移和上线：1 周

## 7. 假设和依赖

### 7.1 假设
- 现有系统的数据库结构可以访问和修改
- 现有系统的业务逻辑可以理解和重构
- 用户可以接受一定程度的界面调整和学习成本
- 数据迁移期间可以暂停部分功能的使用

### 7.2 依赖
- 依赖现有系统的数据库访问权限

## 8. 附录

### 8.1 术语表
- **项目**：测试平台中的项目管理单元，包含项目基本信息、成员、环境等
- **项目类型**：项目的分类，包括接口测试、UI自动化、性能测试、通用项目等
- **定时任务**：按照预定规则自动执行测试任务的调度机制
- **任务类型**：定时任务的分类，包括接口测试、UI自动化、性能测试等
- **通知配置**：配置通知渠道和通知规则的设置
- **测试报告**：记录测试执行结果的文档，包括统计数据、详细日志、图表等
